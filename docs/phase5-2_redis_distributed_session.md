# Phase 5-2: 分散環境でのセッション外部ストア化（Redis & SessionHandlerInterface）

## 1. 背景とアーキテクチャの課題

### ① 単一サーバー（ローカルファイル）セッションの限界
PHPのデフォルト設定（`session.save_handler = files`）では、セッションデータはWebサーバーのローカルディスク（`/tmp` や `/var/lib/php/sessions`）に保存されます。

しかし、クラウド環境や実務の本番Webサービスにおいて、トラフィック増加に伴いサーバーをスケールアウト（複数台へ増設）すると、以下の問題が必ず発生します。

```
[クライアント (ブラウザ)]
       │
       ▼
 [ロードバランサー (ALB等)]
  /            \
 ▼              ▼
[Webサーバー A]  [Webサーバー B]
(sess_xxxあり)    (sess_xxxなし ➔ ログアウト扱いに！)
```

1. **セッションの分断（意図しないログアウト）**:
   - サーバーAでログインしても、次のリクエストがロードバランサーによってサーバーBに振り分けられると、サーバーBにはセッションファイルが存在しないため、「未ログイン」と判定されてしまいます。
2. **Sticky Session（セッション維持機能）の弊害**:
   - ロードバランサーで特定のクライアントを常に同一サーバーに縛り付ける設定（Sticky Session）もありますが、特定サーバーへの負荷偏りが発生し、オートスケーリングの恩恵（サーバーの安全な停止や追加）を妨げる原因になります。

---

### ② 解決策: 分散インメモリKVS（Redis）への外部集約
セッションデータを各Webサーバーのディスクから外部の高速なインメモリKVS（Redis）へ集約することで、Webサーバー自体を**ステートレス（状態を持たない）**に保ちます。

```
[クライアント (ブラウザ)]
       │
       ▼
 [ロードバランサー]
  /            \
 ▼              ▼
[Webサーバー A]  [Webサーバー B]
  \            /
   ▼          ▼
[Redis セッションストア (sess:xxx)]
 (どのサーバーからでも同一セッションを参照・更新可能)
```

---

## 2. セキュリティにおけるRedisセッションの決定的なメリット

分散セッションの導入は、スケーラビリティだけでなく**セキュリティ統制の面でも絶大な効果**を発揮します。

### 1. セッションの集中即時無効化（Centralized Session Revocation）
- **ファイル管理の場合**: サーバーが10台あれば、セッションファイルは分散して存在するため、「特定ユーザーのアカウント乗っ取りを検知して即座にログアウトさせる」ことが困難です。
- **Redis管理の場合**: 管理者画面やAPIから `Redis::del('sess:' . $sessionId)` を実行するだけで、**世界中のどのサーバー・ロードバランサーを経由してアクセスしてこようと、その瞬間にセッションが無効化（強制ログアウト）**されます。
- パスワード変更時や、不審なIPからのアクセス検知時に「全端末から即時ログアウト」を実現する必須の基盤です。

### 2. 有効期限（TTL）の厳格な保証
- **PHP標準（ファイル）**: `session.gc_probability / session.gc_divisor` という「リクエスト発生時の確率（デフォルト1/100や1/1000）」でバックグラウンド掃除を行うため、有効期限が切れた古いセッションファイルがディスク上に何日も残り続けるリスクがあります。
- **Redis**: `SETEX` コマンドによりキーごとにTTL（Time To Live）がミリ秒単位で厳密に管理され、期限が切れた瞬間にRedisエンジンによって確実にメモリから破棄されます。

## 3. 実装の深層: `SessionHandlerInterface` とPHPのライフサイクル

PHPでは `SessionHandlerInterface` を実装したカスタムクラスを作成し、`session_set_save_handler()` に渡すことで、内部のセッション読み書き処理を完全にカスタマイズできます。

```php
interface SessionHandlerInterface {
    public function open(string $path, string $name): bool;
    public function close(): bool;
    public function read(string $id): string|false;
    public function write(string $id, string $data): bool;
    public function destroy(string $id): bool;
    public function gc(int $max_lifetime): int|false;
}
```

### 実装時に直面する重要な落とし穴とベストプラクティス

#### ① `read()` メソッドの戻り値
- Redisの `$redis->get($key)` は、キーが存在しない時に `false` を返します。
- しかし、PHPの `SessionHandlerInterface::read()` が `false` を返すと、PHPは「読み込み障害が発生した」とみなして Warning を発し、`session_start()` が失敗します。
- **対策**: セッションが未作成のときは、必ず **空文字列（`""`）** を返す必要があります。
  ```php
  return ($data === false || $data === null) ? '' : (string)$data;
  ```

#### ② PHPのセッション書き込みタイミング（Shutdown時）
- `$_SESSION` にデータを代入した直後は、まだメモリ上の変数に保持されているだけであり、ストレージへの書き込み（`write()`）は**スクリプトの実行が終了する瞬間（shutdown）**に行われます。
- そのため、スクリプト実行中に最新のストレージ実体を同期・確定させたい場合や、セッションロックを即座に解放したい場合は、**`session_write_close()`** を明示的に呼び出します。

#### ③ 外部削除（Revoke）時のセッション復活（ゴースト）現象
- PHP実行中に外部から `Redis::del($key)` を行っても、スクリプト終了時にPHPエンジンが親切に `write()` を自動実行し、現在の `$_SESSION` の中身でキーを再保存（復活）させてしまいます。
- **対策**: 集中削除を行う際は、メモリ上の `$_SESSION = []` を初期化し、`session_destroy()` を併せて呼ぶことで再書き込みを防止します。

## 4. 実験と検証結果

| 検証項目 | モード A (ローカルファイル) | モード B (Redis外部ストア) |
| :--- | :--- | :--- |
| **保存場所** | 単一サーバーの `/tmp/sess_xxx` | 分散KVS `sess:xxx`（ネットワーク越しに共有） |
| **複数サーバー対応** | ❌ 他サーバーにリクエストが飛ぶと即座にセッション喪失 | ⭕ 全Webサーバーが共通のRedisを参照するため永続化 |
| **有効期限（TTL）** | ⚠️ PHPの確率的ガベージコレクション（古いデータが残りうる） | 🟢 Redisの `SETEX` による厳密な秒単位TTL消去 |
| **管理者による集中強制破棄** | ❌ 他サーバー上のセッションファイルを消去できない | 🛡️ **即時無効化成功**（`Redis::del` で瞬時に全拠点から締め出し） |

## 5. まとめと実務での活用

本演習をもって、Phase 1からPhase 5までの全セキュリティハンズオンが完了しました！

- **Web層の防御**: XSS, CSRF, クリックジャッキング, キャッシュ制御, セキュアヘッダー
- **ネットワーク・通信層**: Cookie保護属性, SOP/CORS, HTTPS/HSTS, プロキシIP偽装, SSRF
- **データ・認証層**: SQLインジェクション, パスワードハッシュ化, レートリミット, 認可制御（IDOR/RBAC）
- **ステート・分散基盤**: Redis分散セッションによるセキュアなスケールアウト基盤

単に「攻撃を防ぐコード」を書くだけでなく、HTTPプロトコル、ブラウザのセキュリティモデル、プロキシやKVSといったインフラ全体の協調動作を理解した多層防御こそが、安全で堅牢なWebアプリケーションを構築する鍵となります。
