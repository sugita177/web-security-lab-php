# Phase 3-1: パスワード暗号学的ハッシュ化と安全な認証基盤

## 1. 概要
前回のPhase 2-3（SQLインジェクション）では、データベースから平文のパスワードがそのまま漏洩してしまう危険を目の当たりにしました。
万が一データベースが侵害されてもユーザーのアカウントとパスワードを守るため、**「安全なパスワードハッシュ化の暗号学」** を学びました。
単純ハッシュ（MD5, SHA-256）やレインボーテーブルの危険性を実証し、`password_hash()` / `password_verify()`（BCRYPT / Argon2id）によるソルト・ストレッチング・自動アップグレード設計を体得しました。

---

## 2. パスワード保存の歴史的変遷と脆弱性

| 方式 | 仕組み | 脆弱性・リスク |
| :--- | :--- | :--- |
| **① 平文（Plaintext）** | 入力された文字列をそのままDBに保存 | DB漏洩時に全員のアカウントが即座に乗っ取られる（最悪） |
| **② 単純ハッシュ（MD5, SHA-1, SHA-256）** | 一方向ハッシュ関数を通した値を保存 | **レインボーテーブル（事前計算済みの巨大逆引き辞書）** で一瞬で平文が復元される。<br>また、GPU等で毎秒数十億回試行できるため総当たりに耐えられない |
| **③ 固定ソルト + ハッシュ** | `sha256($password . "secret_salt")` | レインボーテーブルは防げるが、ソースコード流出時に無力化。<br>また、SHA-256自体の計算速度が速すぎるためGPU総当たりで突破される |
| **④ 暗号学的パスワードハッシュ（BCRYPT, Argon2id）** | ユーザーごとにランダムソルト自動生成 ＋ 何千回ものストレッチング（意図的な低速化） ＋ メモリ負荷 | 現代の標準。レインボーテーブルは完全に無効化され、GPU総当たり攻撃のコストを天文学的に引き上げる |

---

## 3. 防御の要点
1. **意図的な低速化（ストレッチング）とコスト調整**:
   - 暗号学的ハッシュ関数は「計算に一定の時間（例: 0.1秒〜0.5秒）」がかかるように設計されている。
   - 一般ユーザーのログイン（1回）では0.1秒は気にならないが、攻撃者が1億回の総当たりを試す場合は数年かかる計算量になる。
2. **PHPの標準関数群の活用**:
   - `password_hash($password, PASSWORD_DEFAULT)`（PHP 8.5では BCRYPT または Argon2id が標準）
   - `password_verify($password, $hash)`（タイミング攻撃耐性付きの一致検証）
   - `password_needs_rehash($hash, $algo, $options)`（将来マシンスペックが向上した際、ログイン成功時に自動でより強固なコスト/アルゴリズムへ再ハッシュ化・更新する仕組み）

## 4. 実験と検証結果

### (1) レインボーテーブルによるMD5の即時解読
初期ユーザー Alice のMD5ハッシュ `482c811da5d5b4bc6d497ffa98491e38` に対し、事前計算辞書（レインボーテーブル）を当てることで、一瞬で平文 `password123` が逆引き特定される危険を実証した。

### (2) `password_hash()` が生成するハッシュ文字列の解読
生成されたハッシュ値（例: `$2y$12$ZhZQENy6pcpJ47spCUPe.eU03P1LfZtJE55RM6ftCS108MEkjcPOu`）の構造：

```text
 $2y$   12$   ZhZQENy6pcpJ47spCUPe.e   U03P1LfZtJE55RM6ftCS108MEkjcPOu
 ──┬─   ─┬─   ──────────┬───────────   ────────────────┬───────────────
   │     │              │                              │
   │     │              │                              └─ 31文字: ハッシュ値本体
   │     │              └─ 22文字: 自動生成されたランダムソルト
   │     └─ コスト（ストレッチング回数: 2^12 = 4,096回ループ）
   └─ アルゴリズム識別子（2y = BCRYPT）
```
- **ソルトがハッシュ文字列内に自動パッキングされている** ため、DBにソルト用カラムを個別作成する必要がない。
- 同じパスワードであっても、登録のたびに異なるランダムソルトが付与されるため、生成されるハッシュ値は毎回完全に異なる。

### (3) `password_needs_rehash()` による無停止マイグレーション
平文パスワードをDBに保持しない以上、管理者が全ユーザーを一括再ハッシュ化することは不可能。
ユーザーがログインに成功した瞬間（＝平文パスワードが手元にある一瞬）に `password_needs_rehash()` を判定し、最新のコスト設定（`cost => 12`）や最新アルゴリズムで自動上書き保存することで、サービスを停止させずにセキュリティ強度を最新化できる設計を体得した。

## 5. セキュリティ上の超重要原則

### ① パスワードハッシュに「高速性」は致命傷
- SHA-256等の高速ハッシュはファイル整合性検証向けであり、GPUで毎秒数十億回の総当たりが可能なためパスワード保存には使ってはならない。
- パスワードハッシュには、あえて一定の計算時間（約0.1秒）を要するストレッチング機能（BCRYPT / Argon2id）が必須。

### ② ソルトの自作・固定化は厳禁
- `md5($salt . $password)` などの独自方式は、ソルト流出時にレインボーテーブルで即死する。
- 現代のプログラミングでは、暗号学の専門家が設計した `password_hash()` / `password_verify()` にすべて任せるのが絶対原則（Don't roll your own crypto）。
