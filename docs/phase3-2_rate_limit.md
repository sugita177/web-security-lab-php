# Phase 3-2: ブルートフォース攻撃とレートリミット・多層防御

## 1. 背景と脅威シナリオ

### ① ブルートフォース攻撃（Brute-force Attack）と パスワードスプレー（Password Spraying）
- **ブルートフォース攻撃（総当たり攻撃）**:
  単一のアカウント（例: `admin`）に対して、辞書リストやパスワード候補を総当たりで次々に試行し、認証突破を狙う攻撃。
- **パスワードスプレー攻撃（Password Spraying）**:
  多数のアカウント（例: 社員一覧のユーザー名）に対して、よくある共通パスワード（`Password123!` や `Summer2026!` など）を1〜2回ずつ広く浅く試行する攻撃。
  ※ 各アカウントへの試行が1〜2回で終わるため、「5回連続失敗でロック」のようなアカウントロックアウトをすり抜ける特徴を持つ。

### ② なぜインフラ層（Nginx）とアプリ層（PHP）の「多層防御」が必要なのか？
1. **Nginx層（Webサーバー）の役割**:
   - 高速なインメモリ（共有メモリゾーン）でIPアドレスごとのリクエスト頻度を監視。
   - アプリケーション（PHPプロセスやデータベース）に到達する前に過剰なトラフィックを遮断（HTTP 429 Too Many Requests を返却）。
   - WebサーバーやDBのリソース枯渇（DoS）を防ぐ。
2. **PHPアプリ層の役割**:
   - 攻撃者がレートリミットに引っかからないよう低速（0.6秒間隔など）で試行してきた場合や、分散プロキシ・ボットネット経由でIPを偽装・分散してきた場合、NginxのIP単位の制限だけではすり抜けてしまう。
   - アカウント単位（ユーザー名単位）で認証失敗回数をトラッキングし、一時的にアカウントをロックして侵入を完全に阻止する。

```
[ クライアント・攻撃者 ]
        │
        ▼ (大量リクエスト連打: 秒間10回〜)
┌──────────────────────────────────────────────┐
│ ① Nginx層 (インフラ防御)                      │
│   limit_req_zone / limit_req                 │
│   - IPごとの漏れバケツ (2r/s, burst=5)       │
│   - 許容超過時: HTTP 429 Too Many Requests   │
│   ★ PHPに到達する前にWebサーバーで即座に遮断 │
└──────────────────────┬───────────────────────┘
                       │ (許容レート内: 秒間2回以下)
                       ▼
┌──────────────────────────────────────────────┐
│ ② PHPアプリケーション層 (アプリ防御)           │
│   アカウントロックアウト機構                  │
│   - ユーザーごとの連続失敗カウント (上限3回) │
│   - ロック有効期限 (60秒間)                  │
│   ★ 正解パスワードでもロック中は侵入不可     │
└──────────────────────────────────────────────┘
```

## 2. 実装の要点

### ① Nginx レートリミット（Leaky Bucket アルゴリズム）
`docker/nginx/default.conf`:
```nginx
# IPアドレス（バイナリ形式）をキーに10MBの共有メモリゾーンを作成、基準レートは秒間2回
limit_req_zone $binary_remote_addr zone=login_limit:10m rate=2r/s;

server {
    ...
    location ~ \.php$ {
        # バースト枠として最大5リクエストを許容、遅延なし（即時処理）、超過時は429を返す
        limit_req zone=login_limit burst=5 nodelay;
        limit_req_status 429;
        ...
    }
}
```
- **$binary_remote_addr**: テキスト形式（`$remote_addr`: 7〜15バイト）に比べ、バイナリ形式（IPv4で4バイト）でメモリ消費を半分以下に節約。10MBで約16万個のIPを記録可能。
- **1 (通常レート) + 5 (burst枠) = 6回**: 瞬間的なアクセスは6回まで `200 OK` で通過し、7回目以降は即座に `429 Too Many Requests` で遮断。

### ② アプリケーション側のアカウントロックアウト
`src/phase3/3-2_rate_limit.php`:
- **重要設計**: 試行回数を `$_SESSION` に記録してはならない。セッションに記録すると、攻撃者がCookieを送信しない `curl` や毎回Cookieを削除するスクリプトを実行した際に、毎回「新規ユーザー」と判定されて容易にバイパスされてしまう。
- **永続ストレージ**: サーバー側ファイル（`login_attempts.json`）またはデータベース / Redis 等に `username => ['failed_count' => int, 'locked_until' => timestamp]` として保持する。
- **ロック判定**:
  ```php
  $isLocked = !empty($userAttempt['locked_until']) && $userAttempt['locked_until'] > $currentTime;
  ```
- **成功時のクリア**: ログイン成功時に `failed_count = 0`, `locked_until = null` にリセット。
- **失敗時のカウントとロック**:
  ```php
  $userAttempt['failed_count']++;
  if ($userAttempt['failed_count'] >= $maxAttempts) {
      $userAttempt['locked_until'] = $currentTime + $lockoutSeconds;
  }
  ```

## 3. 実験と検証結果

### 実験 ①: Nginx IPレートリミットによる HTTP 429 遮断
```bash
for i in {1..10}; do curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/phase3/3-2_rate_limit.php; done
```
**実行結果**:
```text
200
200
200
200
200
200
429
429
429
429
```
- 基準枠1回 ＋ バースト許容枠5回 ＝ 計6回が `200 OK` を返し、7回目以降はNginxが即座に `429 Too Many Requests` で遮断することを確認。

### 実験 ②: 低速辞書攻撃に対する PHP アカウントロックアウト
```bash
for pass in 123456 password admin123 secret123; do
  echo "=== 試行パスワード: $pass ==="
  curl -s -X POST http://localhost:8080/phase3/3-2_rate_limit.php \
    -d "username=admin&password=$pass&login=1" | sed -n '/class="alert alert-/,/<\/div>/p' | tr -d '\n'
  echo -e "\n"
  sleep 0.6
done
```
**実行結果**:
1. `123456`: 警告（あと 2 回失敗するとロック）
2. `password`: 警告（あと 1 回失敗するとロック）
3. `admin123`: **アカウントを60秒間ロック**
4. `secret123`（正解パスワード）: **「このアカウントは連続認証失敗によりロックされています」**
   ➔ 0.6秒間隔でNginxのIP制限をすり抜けて辞書攻撃を行っても、アプリ層でアカウントがロックされ、正解パスワードが入力されても不正ログインを遮断できることを実証。

## 4. 実務における注意点（アカウントロックDoSへの対策）
- アカウントロックアウトを安易に導入すると、悪意ある第三者がターゲットのアカウント名を意図的に失敗させ続け、**正規ユーザーを恒久的に締め出す「アカウントロックDoS（アカウント枯渇攻撃）」** が成立するリスクがある。
- **実務での緩和アプローチ**:
  1. **CAPTCHA（画像認証 / Turnstile / reCAPTCHA）**: 失敗回数が一定数に達したら、ロックするのではなく「CAPTCHA入力」を必須にし、人間であればログインを継続可能にする。
  2. **指数バックオフ（Exponential Backoff）**: 失敗するごとに「1秒待機 → 2秒待機 → 4秒待機...」と待機時間を倍々に延ばし、総当たりを非現実的な試行速度に落とす。
  3. **IP・ユーザーの複合判定**: 該当IPからの試行のみを遮断し、正規ユーザーの普段のアクセス元からのログインは許可する。
