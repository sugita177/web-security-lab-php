# Phase 4-3: プロキシヘッダーと信頼性境界（IP偽装バイパス）

## 1. 背景とアーキテクチャの課題

### ① リバースプロキシ環境における接続元IPの隠蔽
現代のWebアーキテクチャ（AWS ALB、Cloudflare、Nginxなどの背後にPHP-FPMやLaravelが存在する構成）では、アプリケーションサーバーから見た直接のTCP接続元（`$_SERVER['REMOTE_ADDR']`）は、**「直前のプロキシの内部IP」** になってしまいます。

```text
[クライアント (真のIP: 203.0.113.1)]
          │
          ▼ (TCP接続)
[リバースプロキシ (Nginx / ALB)]
          │
          ▼ (内部通信: REMOTE_ADDR はプロキシのIP 127.0.0.1 になる)
[アプリケーション (PHP / Laravel)]
```

そのため、リバースプロキシは「真のクライアントIP」を伝達するために、以下のHTTPヘッダーを付与・追記して中継します：
- `X-Forwarded-For: <クライアントIP>, <プロキシ1>, <プロキシ2>`
- `X-Real-IP: <クライアントIP>`

---

## 2. 脅威シナリオ：2大IPスプーフィング攻撃

アプリケーションが「社内限定管理画面のIP制限」や「ブルートフォース対策のレートリミット」を実装する際、プロキシヘッダーの扱いを誤ると致命的なIP偽装脆弱性（IP Spoofing）が生じます。

### 攻撃シナリオ A: 外部直接アクセス（プロキシ迂回攻撃）
- **攻撃経路**:
  クラウドのセキュリティグループ設定ミス等により、背後のWebサーバーのポートがインターネットに直接露出している場合、攻撃者はプロキシを経由せず直接アクセスします。
- **手法**:
  攻撃者は `X-Forwarded-For: 192.168.100.50`（許可された社内IP）を自作して送信します。
- **脆弱性**:
  Webサーバーが「X-Forwarded-For があるからこれを使おう」と無批判にヘッダーを採用すると、社内IP制限をあっさり突破されます。

### 攻撃シナリオ B: 正規プロキシ経由でのヘッダー偽造攻撃（多段プロキシ盲点）
- **攻撃経路**:
  攻撃者は正規のリバースプロキシ（Nginx / ALB）を経由してアクセスします。
- **手法**:
  攻撃者は自身のリクエストに `X-Forwarded-For: 192.168.100.50` を付与して送信します。
  プロキシ（Nginx等）の標準設定（`$proxy_add_x_forwarded_for`）は「既存ヘッダーの末尾に接続元IPを追記する」ため、PHPには以下のヘッダーが届きます：
  ```http
  X-Forwarded-For: 192.168.100.50, 203.0.113.1
  ```
  （先頭が攻撃者の捏造値、末尾がプロキシが記録した本物の攻撃者IP）
- **致命的な実装ミス**:
  多くの開発者が `explode(',', $xff)[0]`（先頭のIP）を採用してしまい、**正規プロキシ経由であっても攻撃が成立** してしまいます。

## 3. 安全な防御実装（多層防御）

### ① 信頼境界（Trust Boundary）の厳格な検証
「直前の接続元（`REMOTE_ADDR`）が、自社で管理している信頼できるプロキシ（`TRUSTED_PROXIES`）であるか」を最初に必ず検証します。信頼できない外部から届いたリクエストの `X-Forwarded-For` は **100%ゴミデータ（攻撃パケット）** として完全に無視します。

### ② 末尾（右端）からのIP解決
信頼できるプロキシを経由してきた場合、プロキシが追記した最も信頼できるIPは **末尾（右端）** です。

```php
function getClientIpSecure(): string {
    $remoteAddr = $_SERVER['REMOTE_ADDR'] ?? '0.0.0.0';

    // 1. 直前の接続元が信頼できるプロキシか検証（シナリオAの防御）
    $isFromTrustedProxy = in_array($remoteAddr, TRUSTED_PROXIES, true);

    // 2. 信頼できるプロキシ経由の場合のみヘッダーを参照し、末尾のIPを採用（シナリオBの防御）
    if ($isFromTrustedProxy && !empty($_SERVER['HTTP_X_FORWARDED_FOR'])) {
        $ips = explode(',', $_SERVER['HTTP_X_FORWARDED_FOR']);
        return trim(end($ips)); // ★ 末尾を採用
    }

    // 信頼できない外部からの直接接続は、ヘッダーを無視して直の接続元IPを返す
    return $remoteAddr;
}
```

## 4. 実務フレームワーク（Laravel）での知見

Laravel等のモダンフレームワークでは、この信頼境界は **`TrustProxies` ミドルウェア** で管理されています：

```php
// app/Http/Middleware/TrustProxies.php (Laravel)
protected $proxies = [
    '192.168.1.1',     // 自社のロードバランサーのプライベートIP
    '10.0.0.0/8',
];

protected $headers = Request::HEADER_X_FORWARDED_FOR | Request::HEADER_X_FORWARDED_PROTO;
```

> [!WARNING]
> もし `$proxies = '*'`（すべてのプロキシを信頼）と設定したまま、アプリケーションがAWS ALB等の背後ではなく直接インターネットに露出している場合、外部の誰でも `X-Forwarded-For` を偽装してIP制限を突破できるようになります。実務でも頻出するインフラ設定ミスです。

---

## 5. ゼロトラスト思想と多層防御の原則

IPアドレスによるアクセス制限は、**「そのIPアドレスを持つ端末から届いたこと」** しか保証しません。
端末がマルウェアに感染して「踏み台」にされたり、社内ネットワークに侵入された場合、IP制限は無力化されます。

- **IP制限の役割**: 全世界からの不正スキャンや無差別ブルートフォースを遮断する「第一関門のフィルター」。
- **必須の多層防御**: たとえ許可IPからのアクセスであっても、**ID/パスワード認証 + 多要素認証（MFA）** やクライアント証明書を組み合わせる設計が不可欠です。
